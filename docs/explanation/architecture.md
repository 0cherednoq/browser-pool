# Устройство пула

Из каких частей состоит пул и что происходит с одной арендой.

## Три слоя ответственности

| Слой | Знает | Не знает |
|---|---|---|
| SDK сайта (пишете вы) | адреса, селекторы, как войти, как понять, что сессия жива, как выполнить действие на странице | где открыта страница, в каком контексте, через какой прокси, сколько браузеров |
| `browser-pool` | сколько браузеров, контекстов и вкладок, чей контекст, какой прокси, когда сохранять состояние, что перезапускать | ни одного селектора, ни одного адреса, API страницы |
| Драйвер | как в конкретном SDK запустить браузер, создать контекст с прокси, снять куки | логику приложения и правила пула |

Пул не оборачивает API страницы. Арендатор получает нативный объект SDK, и код сайта пишется под этот SDK. Единого
`click` и `fill` поверх разных SDK в библиотеке нет.

## Части пула

```{mermaid}
flowchart TB
    app["Приложение"] --> pool["BrowserPool"]
    pool --> scheduler["Планировщик"]
    pool --> supervisor["Супервизор"]
    pool --> contexts["Контексты и вкладки"]
    pool --> sessions["Сессии"]
    pool --> proxies["Прокси"]
    pool --> events["События и снимок"]
    supervisor --> driver["Драйвер"]
    contexts --> driver
    provider["Провайдер эндпоинтов"] -.-> driver
    driver --> sdk["Playwright, pydoll, свой SDK"]
```

- Планировщик держит очередь заявок с приоритетами, выбирает кандидата из `any_of`, следит за потолками и
  поколениями контекстов.
- Супервизор следит за здоровьем браузеров: проверяет их по расписанию, отправляет в карантин, перезапускает,
  проводит плановую смену и закрывает простаивающие.
- Слой контекстов открывает контексты identity и запускает под них браузеры, закрывает контексты по простою,
  вытесняет давно не работавшие и хранит запас тёплых вкладок.
- Слой сессий соединяет `SessionFlow` с хранилищем состояния.
- Слой прокси берёт прокси из источника, помнит привязку к identity и сообщает источнику о сбоях.
- Наблюдение включает шину событий, `pool.snapshot()` и поиск аренд, которые не возвращаются.

Почти всё это лежит в `browser_pool._core` и публичным API не является. Наружу смотрят `BrowserPool` и типы
событий.

## Путь одной аренды

1. Заявка `pool.page(identity)` попадает к планировщику. Если вкладку можно выдать сразу, очередь не нужна.
2. Для `any_of` планировщик сначала берёт identity с уже открытым контекстом, потом новую.
3. Новый контекст размещается в самом свободном здоровом браузере: где меньше занятых вкладок, затем где меньше
   контекстов. Если процесс этого браузера ещё не запущен, пул запускает его сейчас.
4. Перед открытием контекста берётся замок identity. Пул читает из хранилища сохранённое состояние, выбирает прокси
   и просит драйвер создать контекст сразу с этим состоянием.
5. `SessionFlow.open` делает контекст рабочим. После успешного открытия пул сохраняет состояние.
6. Арендатор получает тёплую вкладку из запаса или новую, для которой один раз вызывается `prepare_page`.
7. На выходе из `async with` вкладка проходит `reset_page` и возвращается в запас. Если из блока вылетело
   исключение, вкладка закрывается, пул определяет вид сбоя и выполняет реакцию.

Шаги 4 и 5 выполняются один раз на контекст. Пока они идут, остальные заявки этой identity ждут и получают готовый
контекст.

## Жизнь браузера

Пул держит столько слотов браузеров, сколько задано в `Topology.browsers`. Слот существует с самого начала в
состоянии `healthy`, а процесс в нём запускается лениво, когда понадобился первый контекст.

```{mermaid}
stateDiagram-v2
    [*] --> healthy
    healthy --> draining: плановая смена, простой
    draining --> healthy: закрыт по простою
    draining --> restarting: плановая смена
    healthy --> quarantined: умер или завис
    draining --> quarantined
    quarantined --> restarting
    restarting --> healthy
    restarting --> quarantined: запуск не удался
    healthy --> stopped: слот убран
```

Новые аренды получает только браузер в состоянии `healthy`. Проверка здоровья опрашивает драйвер по расписанию, а
если SDK сам сообщает об обрыве соединения, пул узнаёт о падении сразу.

В карантине браузер не получает новых задач, а его контексты выводятся из работы. Пул ждёт, пока арендаторы вернут
вкладки, закрывает процесс и запускает его заново. Если запуск не удался, браузер возвращается в карантин, и пауза
перед следующей попыткой растёт.

Плановая смена идёт мягче: браузер дорабатывает выданные аренды, состояние сессий сохраняется до закрытия.
Одновременно меняется один браузер, и только когда остальные здоровы.

Простаивающий браузер закрывается, а его слот остаётся `healthy`: процесс запустится снова, когда придёт заявка.
В `stopped` слот переходит из любого состояния, когда `pool.resize` уменьшает число браузеров.

На каждое действие есть таймаут: запуск, открытие сессии, создание вкладки, закрытие, перезапуск, дренаж. Зависшее
закрытие пул не ждёт вечно. Сбой закрытия вкладки попадает в лог и в счётчик `close_failures` снимка. Если не
закрылся браузер, процесс убивается вместе с деревом дочерних.

## Остановка

`await pool.stop()` перестаёт принимать заявки, отменяет ожидающих (`PoolStoppedError`), ждёт занятые аренды,
сохраняет состояния и закрывает контексты, браузеры и драйвер. `await pool.terminate()` закрывает всё сразу, не
дожидаясь аренд. Выход из `async with pool` делает то же, что `stop()`.

## Слои кода

Зависимости между модулями идут сверху вниз, и это проверяет `poe arch` (import-linter).

| Слой | Модули | Правило |
|---|---|---|
| адаптеры | `drivers`, `providers`, `monitors`, `testing` | знают всё ниже, друг о друге не знают |
| фасад | `pool` | собирает ядро, окна и хуки |
| оркестрация | `browser_pool._core`, `windows` | независимы: раскладка окон не влияет на аренду |
| контракты и модель | `flow`, `driver`, `provider`, `host`, `evidence`, `identity`, `lease`, `hooks`, `config`, `events`, `snapshot`, `errors` | импортируют друг друга, но не вверх |
| предметные листья | `state`, `proxies`, `geometry`, `locks`, `procguard`, `debug` | не знают ни про пул, ни друг про друга |
| фундамент | `clock` | без зависимостей |

Ядро импортирует только стандартную библиотеку. SDK браузеров подключаются в адаптерах и только лениво, внутри
функций, поэтому процесс без браузера не тянет за собой Playwright.

## Время и конкурентность

Пул работает в одном цикле событий asyncio. Время внутри пула отсчитывается по монотонным часам: настенное прыгает
от синхронизации и сна машины, и сроки жизни по нему считать нельзя. Часы подменяемы, на этом построено
виртуальное время в тестах. Наружу, в события и записи хранилища, уходит время в UTC.

Фоновые задачи принадлежат пулу и завершаются в `stop()`.

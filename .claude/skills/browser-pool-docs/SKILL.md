# Документация browser-pool

Сайт собирает Sphinx из `docs/`. План работ и принятые решения лежат в `docs/raw/DOCS_PLAN.md`, план оформления в
`docs/raw/DOCS_REDESIGN.md` (рабочие документы владельца, в репозиторий не входят); если они есть на диске,
прочитай в обоих раздел «Что сделано», прежде чем менять структуру.

Образцы оформления: `docs/tutorial/quickstart.md` (учебник) и `docs/guide/proxies.md` (руководство). Новая
страница повторяет их приёмы.

## Куда писать

У каждого каталога свой тип страниц. Тип определяет, с чего она начинается и что в неё не входит.

| Каталог | Тип | Начинается с | Не содержит |
|---|---|---|---|
| `docs/tutorial/` | учебник, раздел меню «Начало» | того, что получится в конце | перечня всех опций |
| `docs/guide/` | руководство по проблеме, раздел «Задачи» | ситуации читателя: что у него болит без пула | объяснений устройства |
| `docs/extending/` | для автора flow, драйвера, провайдера, раздел «Свой код» | задачи и минимального рабочего кода | истории решений |
| `docs/explanation/` | объяснение, раздел «Устройство» | вопроса «почему так» | пошаговых рецептов |
| `docs/reference/` | справочник | таблицы или списка | рассуждений |

`docs/explanation/concepts.md` стоит в меню в разделе «Начало»: это словарь, на его термины ссылаются ролью
`{term}`.

Справочники `reference/config.md`, `events.md`, `errors.md` генерируются из кода (`scripts/config_reference.py`,
`scripts/reference_tables.py`). Чтобы изменить их текст, правь докстринг в `src/browser_pool/` и перегенерируй.
Страницы `reference/api/` состоят из директив `automodule`; новый публичный модуль добавляется туда директивой.

Новая страница добавляется в оглавление `docs/index.md`, иначе сборка упадёт.

## Оформление страницы

Часть этих правил проверяет `tests/test_docs_layout.py`.

**Заголовок и лид.** Заголовок страницы не длиннее 25 знаков: он же пункт бокового меню. Сразу под ним лид, один
абзац в одну строку не длиннее 100 знаков: что читатель получит. Разметки лиду не нужно, первый абзац страницы
оформляет стиль сайта. Ситуация читателя в руководстве идёт вторым абзацем.

**Цветные блоки.** Не больше трёх на страницу, у каждого вида своё назначение:

| Блок | Когда |
|---|---|
| `:::{warning}` | действие необратимо или ведёт к потере аккаунта, денег, данных |
| `:::{important}` | без этого пример не заработает |
| `:::{tip}` | так короче или дешевле, но можно и без этого |
| `:::{note}` | уточнение, которое можно пропустить |

В блок выносится существующее предложение страницы. Новых утверждений ради блока не придумывай; если выносить
нечего, блока нет.

**Вкладки.** `tab-set` из `sphinx-design` с `:sync-group:`. Осей три, других не заводи: `installer` (вкладки `uv`,
`pip`), `driver` (`playwright`, `pydoll`), `preset` (`accounts`, `scraping`). Вкладки ставятся, когда код или
команда различаются по оси; ради одного слова их не ставят.

**Код.**

- Полный файл подключается через `literalinclude` из `examples/` с `:caption:` (имя файла) и `:linenos:`.
  Строки, о которых идёт речь, отмечаются `:emphasize-lines:`.
- Вывод программы лежит файлом в `docs/tutorial/output/` и показывается блоком
  `:::{admonition} Результат запуска` с классом `tip run-result`. Совпадение с настоящим выводом проверяет
  `tests/test_examples.py`.
- Фрагмент на странице остаётся обычным блоком кода с импортами. Пояснение длиннее пяти слов идёт в текст под
  блоком, а не в комментарий.
- В блоках кода, набранных на странице, нет длинного тире: двоеточие, запятая или отдельное предложение. В файлах
  `examples/` оно допустимо, так написан код проекта.

**Перечисления.** Абзац или пункт списка, который перечисляет больше трёх вещей с пояснениями, становится
таблицей или списком с одной вещью в пункте. На страницах раздела «Устройство» связный текст не рубится.

**Ссылки.**

- Имя из справочника API в обратных кавычках (`BrowserPool`, `Limits.max_waiting`, `pool.snapshot()`) само
  становится ссылкой, если такое имя в справочнике одно (`docs/conf.py`). Роли `{class}` и `{meth}` не нужны.
- Термин из словаря при первом упоминании на странице учебника пишется ролью: `` {term}`аренда` ``, в другом
  падеже `` {term}`аренду <аренда>` ``. В руководствах роль не обязательна.

**Конец страницы.** Раздел `## Что дальше` с двумя карточками: следующая страница по порядку чтения и соседняя по
теме или её справочник. Разметку карточек бери из образцов, иконки задаются ролью `{octicon}`.

## Откуда брать факты

Умолчание, предел, имя поля, порядок действий пула берутся из кода (`src/browser_pool/`), требований
(`docs/raw/TZ.md`, если есть на диске) или примеров (`examples/`). Если нужного числа или поведения там нет, в тексте его тоже нет: задай
вопрос владельцу и скажи об этом в итоге работы. Выдуманный проверяемый факт хуже пропуска.

Код в страницах:

- пример из `examples/` подключается директивой `literalinclude` с `:pyobject:`, а не копируется;
- короткий самостоятельный фрагмент пишется в блоке кода с полными импортами;
- вывод программы приводится настоящий: запусти пример и вставь то, что он напечатал.

Имена в обратных кавычках проверяет `tests/test_docs_names.py`: имя должно существовать в коде.

## Словарь

Не переводятся: identity, flow, payload, SDK. Пишутся по-русски: аренда (lease), контекст, вкладка (не «страница»,
когда речь о ресурсе браузера), сессия, драйвер, провайдер, прокси, пул, снимок (snapshot), улики (evidence), вид
сбоя (error kind), вывести из работы (retire), карантин, тёплая вкладка. «SDK сайта» вместо «site SDK».

## Стиль

Действуют жёсткие запреты скилла humanizer-ru, их проверяет `uv run poe prose`:

- длинное тире не используется, вместо него дефис с пробелами или перестроенное предложение;
- стрелки и математические знаки в прозе пишутся словами;
- нет конструкций «не просто X, а Y» и «не только X, но и Y»;
- нет риторических вопросов, двоеточий-подводок, рубленых фрагментов подряд, разделителей между абзацами.

Сверх запретов:

- обращение к читателю на «вы», без похвал и вступлений;
- жирный только для одного-двух мест на странице, не для меток в списках;
- одна мысль в предложении; перечень из трёх и более вариантов с пояснениями оформляется списком или таблицей;
- длинного тире нет и в блоках кода, набранных на странице (правила оформления выше).

Файлы хранятся с окончаниями строк LF.

## Порядок работы

1. Определи тип страницы и её место. Если правишь существующую, сначала прочитай её целиком.
2. Собери факты из кода и примеров. Запиши, чего не нашёл.
3. Напиши текст.
4. Запусти проверки и исправь всё, на что они укажут:

   ```bash
   uv run poe prose
   uv run poe docs
   uv run pytest tests/test_docs_names.py tests/test_docs_api.py tests/test_docs_layout.py
   uv run poe site
   ```

   Для `poe site` нужна группа зависимостей: `uv sync --all-extras --group docs`.
5. Для новой страницы или большой правки прогони `/humanizer-ru`: аудит, затем слепая проверка свежим агентом,
   которому даны только готовый текст и справочник паттернов. Агента попроси сверить с кодом и утверждения о
   поведении пула.
6. Открой собранную страницу в браузере в тёмной и светлой теме: зелёная сборка не значит, что её удобно читать.
7. В итоге перечисли, что изменено, какие проверки запускались и с каким результатом, и чего в коде не нашлось.
